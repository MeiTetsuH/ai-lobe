# Fork maintenance

This fork follows stable upstream release tags. This document records maintenance policy and local patches; it does not certify that a release has been deployed or accepted.

## Two-branch ownership

- `main` is an exact mirror of `upstream/main`, including its original configuration and history. Do not add personal patches, this ledger, dependency overrides, or deployment commits there.
- `deploy/vercel-production` preserves personal changes and merges selected stable upstream tags. It is the only Vercel production branch and the home of this ledger. Review this branch when changing the deployed application.
- Keep only these two long-lived branches. Temporary maintenance branches target the deployment branch and are removed after merge and acceptance. Preserve unique historical commits in verified recovery tags before deleting old branches; do not merge obsolete route-deletion patches merely to archive them.
- Disable automatic Preview Deployments in the Vercel project settings and use a platform-level ignored-build command that proceeds only for `deploy/vercel-production`. The untouched upstream `main` contains its own `vercel.json.ignoreCommand`, which overrides the platform ignored-build command and can allow preview builds to run migrations; the independent project-level preview switch is therefore required.
- Do not re-enable previews until a separate non-production database and secret configuration are in place and their migration boundary has been verified. Check both the tracked production branch and the preview switch before synchronizing `main`; upstream mirroring must never migrate the production database.

The Test CI and E2E workflows include deployment-branch pushes. Application and lockfile changes still need their affected checks and cloud build; moving the branch pointer or updating documentation does not certify product behavior.

## Keep configuration outside the fork

- Prefer supported Vercel environment variables over changes to upstream defaults, model catalogs, UI, or provider adapters.
- Configure file embeddings with `DEFAULT_FILES_CONFIG`, background agents with `SYSTEM_AGENT`, and memory extraction, embeddings, and persona generation with the applicable `MEMORY_USER_MEMORY_*` variables.
- Keep model IDs, provider IDs, endpoint URLs, dimensions, and credentials consistent across each configuration. Changing a chat default does not change every background agent.
- Store credentials only in the deployment's secret configuration. Never commit values, environment exports, private account details, or production conversation data.
- Preserve upstream applications and routing surfaces. Reduce installation and function-tracing scope instead of deleting applications merely to shorten builds.
- Keep necessary source patches small, independently testable, and separate from deployment configuration. Reevaluate every patch at each stable tag.

## Chat image access

`src/services/chat/resolveImageUrls.ts` resolves same-origin `/f/:id` image parts through the authorized readable-URL API before model requests. Providers otherwise fetch the protected application origin and can receive a WAF challenge or 429 even after a successful upload. Resolution is request-scoped, preserves stored message URLs and external images, and stops on authorization failures. The chat abort signal reaches each readable-URL query; cancelled requests never start model inference. Distinct image IDs use sequential batches of at most 100, with one scoped file query and one bulk knowledge-base permission check per batch, and at most eight concurrent storage signatures. The existing single-file readable endpoint remains compatible. Keep the bucket private and retain the firewall. Remove this patch when upstream resolves model-facing image URLs equivalently. Regression checks: `src/services/chat/resolveImageUrls.test.ts`, `src/services/chat/index.completion.test.ts`, `src/services/file/index.readableUrls.test.ts`, and `apps/server/src/routers/lambda/file/readableUrls.test.ts`. Track [upstream PR #21034](https://github.com/lobehub/lobehub/pull/21034); retain the patch until an adopted stable release includes equivalent behavior.

## Stable-tag upgrade procedure

1. Fetch `upstream/main` and stable tags. Record the current production commit, previous upstream tag, target stable tag, and deployment configuration revision. Verify preview deployments are disabled, synchronize the clean `main` mirror without personal commits, and perform the upgrade on a temporary branch from `deploy/vercel-production`. Preserve unrelated working-tree changes and create a recoverable Git reference before merging.
2. Compare all three change sets: the previous tag to current fork, the previous tag to target tag, and the target tag to the proposed fork. Review both upstream changes and retained patches; a clean merge is not proof of compatibility.
3. Check the ledger against upstream behavior. Delete absorbed or obsolete patches instead of carrying them forward automatically. Keep a regression test where it protects an intended fork behavior.
4. Resolve dependency changes using pnpm and the tracked lockfile. Review the complete workspace dependency closure before narrowing installation filters; retain all required web, mobile, auth, share, and workbench dependencies.
5. Run the repository quality command for affected files, owning-package tests, and required type/build checks. Run normal commit hooks; repair failures rather than bypassing hooks or suppressing rules.
6. Review migrations and configuration compatibility before deployment. Do not assume an old application can safely run against a changed schema.
7. Merge into `deploy/vercel-production` and deploy only after the required checks pass. Verify the provider's build and migration result, the promoted commit, and the actual production domain separately. Never merge this deployment branch back into the upstream mirror.
8. Verify real login, text chat, upload/retrieval, search, memory, mobile assets, and sharing where affected. Confirm indexing headers and the intended model/provider route without exposing secrets or private messages. Record evidence and unresolved limitations.
9. Update this ledger with the final retained patches and their removal conditions. Report deployment and acceptance as complete only after their respective evidence exists.

## Security maintenance baseline

- Require Node.js 24.22.1 or a later 24.x security release for local work, CI, and deployment. `.nvmrc`, CI pins, and the Docker default share this minimum. Verify the provider's actual build/runtime version separately.
- Keep every workspace and peer copy of Next.js on 16.4.2 and sharp on 0.35.5. The v2.2.20 upstream ranges alone do not cover the October 2026 Next.js and SVG image-processing advisories.
- Keep Better Auth and its Expo/passkey plugins on the same patched 1.6.x version. Keep the reviewed transitive security overrides in `pnpm-workspace.yaml`; regenerate and verify the frozen lockfile after changing them.
- Keep Undici 7.x on 7.30.1 or later for CVE-2026-109869, including direct HTTP/proxy use and nested Expo, Electron and Miniflare copies. The independent desktop workspace also requires 6.29.1, 7.30.1 and 8.12.2 within each existing major; its lockfile and overrides are separate from the web workspace.
- Keep Zod 4.x on 4.6.6 and body-parser on patched versions within each existing major. The desktop lock also carries compatible Electron, Vite, MCP SDK, DOMPurify, gRPC and URL-parser security updates. Do not force legacy Zod 3.x, tar 6.x, Happy DOM 20.x or pre-1.0 dependency families across compatibility boundaries to hide audit findings.
- The obsolete Ant Design icon pin is removed together with the old locale chunk split; the root UI override remains.
- Keep the mobile SPA build, the root UI override, private readable-file URLs, request-scoped image signing, OpenAI embedding routing, RAG streaming, memory credential precedence, and hashed automatic cache keys. Upstream's one-shot LLM relay and PDF chunk highlighting compose with these patches.
- v2.2.20 already caps BM25 keyword-search page sizes at 8192. Retain the upstream implementation and the matching-result regression cases for the default, an explicit oversized request, and a subsequent page. PGlite and mocked query results do not certify ParadeDB integration; the server database CI must also pass.
- Dependency audits are evidence about the resolved graph, not proof that every advisory is exploitable in the deployed application. Do not force incompatible major versions or delete optional integrations solely to obtain a zero count. Record unpatched or incompatible dependency paths in release evidence.
- `build:vercel` runs database migrations after building. Use `build:raw` for a local build without migration, and review the stable release's new migrations and backup/rollback plan before authorizing deployment.

The retained security changes live in `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml` and the independent `apps/desktop` manifest/workspace/lock files. Runtime-version requirements also live in `.nvmrc`, CI pins and the Docker default. Reevaluate these overrides against each stable release and remove only those whose complete resolved dependency graph is equivalently patched. The highlighted-error and compact-action test adaptations remain in their owning test files; they preserve full error text and the UI library's public size contract without changing production rendering.

The desktop `fetch-socks>undici` override stays on patched 8.x to match its existing dispatcher instance and types; a broad `>=7` dependency range must not silently move that caller to 7.x. Root and desktop locks are independent. Ordinary version movement from the stable upstream merge is distinct from targeted security fixes.

Run production dependency audits against `deploy/vercel-production`, including both the root and independent desktop lockfiles. The default `main` branch intentionally mirrors upstream and has no fork overrides; its dependency alerts do not describe the deployment branch's resolved graph.

## Embeddings and rollback

- Before changing an embedding model or dimensions, inventory existing vectors and preserve a recoverable backup of the original vectors and their model configuration, even when the knowledge base appears unused.
- Do not mix vectors from incompatible models. Reindex into a recoverable replacement and validate retrieval before retiring the original index or backup.
- Keep deployment code and environment rollback coordinated. A code rollback alone does not restore model IDs, credentials, endpoints, or dimensions.
- Preserve the prior environment revision securely; record names and intended relationships in release notes, never secret values.
- Restore a matching code/configuration/vector combination. Review database migrations independently and avoid destructive reverse migrations as a routine rollback step.
- After rollback, verify production routing, login, chat, retrieval, and memory again; a successful promotion alone is insufficient.

## Deployment configuration boundaries

These are maintenance instructions, not a copy of any live deployment configuration. Keep real values in the hosting provider's secret/environment settings.

For an eligible Vercel deployment whose required server functions exceed the standard 250 MB bundle limit, use the supported [`VERCEL_SUPPORT_LARGE_FUNCTIONS=1` opt-in](https://vercel.com/docs/functions/limitations#large-functions) in the production environment. It requires Fluid compute with Active CPU and does not support Secure Compute or Static IPs. Keep the existing plan, compute resources, duration limits, and application routes unchanged; only oversized functions use the large-function path. Recheck eligibility and usage limits before deployment. To return to standard bundles, first verify that every required function fits the standard limit, then set the flag to `0` and redeploy. Coordinate any code, environment, and database rollback as described above.

Large-function support does not increase the Hobby limit of 12 functions per deployment. In `v2.2.20`, `VERCEL_ANALYZE_BUILD_OUTPUT=1` showed that `ffmpeg-static` (76.21 MB) and \~150 MB of `.next/server/chunks` pushed eight individual routes past 250 MB uncompressed, preventing `@vercel/next` from packing them into shared Lambdas and producing >12 functions. To keep deployment within 10 functions on Vercel Hobby without affecting web or mobile-browser chat:

- `next.config.ts` excludes `node_modules/.pnpm/ffmpeg-static*/**` and `node_modules/ffmpeg-static/**` from function file tracing.
- `apps/server/src/routers/async/index.ts` omits the unused `video` and `document` sub-routers, and `apps/server/src/router-hono/webhooks/index.ts` retains only the memory pipeline webhooks (`/memory-extraction`, `/memory-user-memory/persona/update-writing`, `/memory-user-memory/pipelines/extract/chat-topic/cancel`).
- Unused heavy route entrypoints `src/app/(backend)/webapi/create-image/comfyui/route.ts`, `src/app/(backend)/trpc/mobile/[trpc]/route.ts` (native React Native app only; mobile browser SPA uses `/trpc/lambda/[trpc]`), `src/app/(backend)/api/acceptance-review/[[...route]]/route.ts`, `src/app/(backend)/api/v1/[[...route]]/route.ts`, and `src/app/(backend)/api/dev/[[...route]]/route.ts` are removed on `deploy/vercel-production`.

### Video creation is disabled in this deployment

Removing the video callback and `ffmpeg-static` alone does not disable submission: the lambda video router, direct API callers, saved tool pins, and server-side agent tools can still submit a provider request that cannot finish locally. This fork disables creation before any generation task or provider request, rather than letting a potentially billable request fail during result processing.

- `packages/const/src/deploymentCapabilities.ts` owns the deployment capability. `VIDEO_GENERATION_ENABLED` is false in this branch and is not a user preference or an environment override. Chat, image generation/recognition, and file processing remain enabled.
- `apps/server/src/services/generation/videoAvailability.ts` rejects creation with `PRECONDITION_FAILED`. Both `routers/lambda/video/index.ts` and the unmounted `routers/async/video.ts` enforce it at the beginning of their create mutation. `routers/lambda/generationTopic.ts` also refuses new video topics before inserting rows. Client and server video tools converge on these guarded routers; old clients cannot bypass this by retaining a creation button.
- `packages/builtin-tools/src/featureGates.ts`, the builtin registry, and `packages/mecha/src/toolSet/manifestPool.ts` hide video from UI/discovery and remove it from all model-facing manifest sources, including saved plugins, additional manifests, and explicit activation. Historical video tool renderers remain registered so old conversations can still display results.
- Home model shortcuts and the image/video mode selector omit video creation. The video page remains available to view/download existing results, but its prompt input becomes a localized disabled notice; new-topic, edit/reuse, and generation-upload actions are disabled or hidden. The wrappers leave the upstream video prompt implementation untouched for a future coordinated restoration.
- `src/features/VideoGenerationInput/` owns that mounting boundary; the existing video page, workspace, and skeleton mount it. `GenerationLayout/Header` accepts a `disableCreate` presentation flag so image generation keeps its existing creation control.
- Regression coverage includes refusal before task writes/provider submission, exclusion from every tool-manifest source, persisted video pins on both browser and server engines, and continued availability of image/file tools. The original video-router tests explicitly enable a mocked capability to retain upstream behavior coverage; a separate test exercises the real disabled deployment setting. The `Test deployment capability boundaries` cloud CI step uses `scripts/vitest.deployment.config.mts` to run package tests that the default App/Server discovery excludes.

Remove this divergence only after intentionally restoring video callbacks, the async pipeline, and the ffmpeg runtime; verifying that the deployment still fits its function and bundle limits; and validating creation, polling/webhook completion, permissions, and historical reads together. Do not enable the capability merely because a newer upstream release or environment setting exposes a video model. Restoring video is a coordinated deployment change, not a settings toggle.

The root Next configuration inlines only the non-secret `LOBE_VERCEL_BUILD` target flag through the supported `env` option. `src/instrumentation.ts` uses it to make the existing Docker/local gateway and agent-transfer startup imports statically unreachable in Vercel builds. Original runtime guards, Docker startup behavior, telemetry, HTTP routes and cron handlers remain intact. Do not inline the full environment or exclude runtime dependencies by filename. Retain the patch until upstream provides the same build boundary; validate its effect against actual cloud function output as well as `src/instrumentation.test.ts` and `scripts/vercelConfiguration.test.ts`.

## Validation and troubleshooting

- Use pnpm for installation and the repository's Bun-based check scripts. Run the owning test files and the repository type check; do not bypass signing or pre-commit hooks.
- An upstream quota or rate-limit response is not necessarily an application defect. Inspect its metric and retry guidance, distinguish per-minute from per-day limits, and avoid repeated retries when the daily allowance is exhausted.
- A provider API probe is useful but does not replace a real application request: the application adds metadata, cache keys, tools, and background work.
- For file-preview failures, distinguish an expired URL, authentication failure, cross-origin redirect, CORS mismatch, and rendering error. Resolve the authenticated readable URL before widening bucket access.
- Upload validation must cover a new file, same-user deduplication, and denied unowned storage operations. Older clients that omit reservation data must update rather than receive an unrestricted compatibility path.
- Vercel `READY`, the production domain's assigned deployment, and a real browser check are separate signals. A successful build does not prove chat, file access, or background workflows are usable.
- Record measured build durations and limitations; a narrower installation or tracing configuration alone does not prove faster builds.
