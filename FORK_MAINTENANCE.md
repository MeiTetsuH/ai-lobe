# Fork maintenance

This fork follows stable upstream release tags. This document records maintenance policy and local patches; it does not certify that a release has been deployed or accepted.

## Keep configuration outside the fork

- Prefer supported Vercel environment variables over changes to upstream defaults, model catalogs, UI, or provider adapters.
- Configure file embeddings with `DEFAULT_FILES_CONFIG`, background agents with `SYSTEM_AGENT`, and memory extraction, embeddings, and persona generation with the applicable `MEMORY_USER_MEMORY_*` variables.
- Keep model IDs, provider IDs, endpoint URLs, dimensions, and credentials consistent across each configuration. Changing a chat default does not change every background agent.
- Store credentials only in the deployment's secret configuration. Never commit values, environment exports, private account details, or production conversation data.
- Preserve upstream applications and routing surfaces. Reduce installation and function-tracing scope instead of deleting applications merely to shorten builds.
- Keep necessary source patches small, independently testable, and separate from deployment configuration. Reevaluate every patch at each stable tag.

## Chat image access

`src/services/chat/resolveImageUrls.ts` resolves same-origin `/f/:id` image parts through the authorized readable-URL API before model requests. Providers otherwise fetch the protected application origin and can receive a WAF challenge or 429 even after a successful upload. Resolution is request-scoped, preserves stored message URLs and external images, and stops on authorization failures. The chat abort signal reaches each readable-URL query; cancelled requests never start model inference. Distinct image IDs use sequential batches of at most 100, with one scoped file query and one bulk knowledge-base permission check per batch, and at most eight concurrent storage signatures. The existing single-file readable endpoint remains compatible. Keep the bucket private and retain the firewall. Remove this patch when upstream resolves model-facing image URLs equivalently. Regression checks: `src/services/chat/resolveImageUrls.test.ts`, `src/services/chat/index.completion.test.ts`, `src/services/file/index.readableUrls.test.ts`, and `apps/server/src/routers/lambda/file/readableUrls.test.ts`. Track [upstream PR #21034](https://github.com/lobehub/lobehub/pull/21034); retain the patch until an adopted stable release includes equivalent behavior.

## Stable-tag upgrade procedure

1. Record the current production commit, previous upstream tag, target stable tag, and deployment configuration revision. Preserve unrelated working-tree changes and create a recoverable Git reference before merging.
2. Compare all three change sets: the previous tag to current fork, the previous tag to target tag, and the target tag to the proposed fork. Review both upstream changes and retained patches; a clean merge is not proof of compatibility.
3. Check the ledger against upstream behavior. Delete absorbed or obsolete patches instead of carrying them forward automatically. Keep a regression test where it protects an intended fork behavior.
4. Resolve dependency changes using pnpm and the tracked lockfile. Review the complete workspace dependency closure before narrowing installation filters; retain all required web, mobile, auth, share, and workbench dependencies.
5. Run the repository quality command for affected files, owning-package tests, and required type/build checks. Run normal commit hooks; repair failures rather than bypassing hooks or suppressing rules.
6. Review migrations and configuration compatibility before deployment. Do not assume an old application can safely run against a changed schema.
7. Deploy only after the required checks pass. Verify the provider's build and migration result, the promoted commit, and the actual production domain separately.
8. Verify real login, text chat, upload/retrieval, search, memory, mobile assets, and sharing where affected. Confirm indexing headers and the intended model/provider route without exposing secrets or private messages. Record evidence and unresolved limitations.
9. Update this ledger with the final retained patches and their removal conditions. Report deployment and acceptance as complete only after their respective evidence exists.

## Security maintenance baseline

- Require Node.js 24.22.1 or a later 24.x security release for local work, CI, and deployment. `.nvmrc`, CI pins, and the Docker default share this minimum. Verify the provider's actual build/runtime version separately.
- Keep every workspace and peer copy of Next.js on 16.4.2 and sharp on 0.35.5. The v2.2.20 upstream ranges alone do not cover the October 2026 Next.js and SVG image-processing advisories.
- Keep Better Auth and its Expo/passkey plugins on the same patched 1.6.x version. Keep the reviewed transitive security overrides in `pnpm-workspace.yaml`; regenerate and verify the frozen lockfile after changing them.
- The obsolete Ant Design icon pin is removed together with the old locale chunk split; the root UI override remains.
- Keep the mobile SPA build, the root UI override, private readable-file URLs, request-scoped image signing, OpenAI embedding routing, RAG streaming, memory credential precedence, and hashed automatic cache keys. Upstream's one-shot LLM relay and PDF chunk highlighting compose with these patches.
- v2.2.20 already caps BM25 keyword-search page sizes at 8192. Retain the upstream implementation and the matching-result regression cases for the default, an explicit oversized request, and a subsequent page. PGlite and mocked query results do not certify ParadeDB integration; the server database CI must also pass.
- Dependency audits are evidence about the resolved graph, not proof that every advisory is exploitable in the deployed application. Do not force incompatible major versions or delete optional integrations solely to obtain a zero count. Record unpatched or incompatible dependency paths in release evidence.
- `build:vercel` runs database migrations after building. Use `build:raw` for a local build without migration, and review the stable release's new migrations and backup/rollback plan before authorizing deployment.

## Embeddings and rollback

- Before changing an embedding model or dimensions, inventory existing vectors and preserve a recoverable backup of the original vectors and their model configuration, even when the knowledge base appears unused.
- Do not mix vectors from incompatible models. Reindex into a recoverable replacement and validate retrieval before retiring the original index or backup.
- Keep deployment code and environment rollback coordinated. A code rollback alone does not restore model IDs, credentials, endpoints, or dimensions.
- Preserve the prior environment revision securely; record names and intended relationships in release notes, never secret values.
- Restore a matching code/configuration/vector combination. Review database migrations independently and avoid destructive reverse migrations as a routine rollback step.
- After rollback, verify production routing, login, chat, retrieval, and memory again; a successful promotion alone is insufficient.

## Validation and troubleshooting

- Use pnpm for installation and the repository's Bun-based check scripts. Run the owning test files and the repository type check; do not bypass signing or pre-commit hooks.
- An upstream quota or rate-limit response is not necessarily an application defect. Inspect its metric and retry guidance, distinguish per-minute from per-day limits, and avoid repeated retries when the daily allowance is exhausted.
- A provider API probe is useful but does not replace a real application request: the application adds metadata, cache keys, tools, and background work.
- For file-preview failures, distinguish an expired URL, authentication failure, cross-origin redirect, CORS mismatch, and rendering error. Resolve the authenticated readable URL before widening bucket access.
- Upload validation must cover a new file, same-user deduplication, and denied unowned storage operations. Older clients that omit reservation data must update rather than receive an unrestricted compatibility path.
- Vercel `READY`, the production domain's assigned deployment, and a real browser check are separate signals. A successful build does not prove chat, file access, or background workflows are usable.
- Record measured build durations and limitations; a narrower installation or tracing configuration alone does not prove faster builds.

## Public documentation policy

Publish only source paths, generic variable names, architectural decisions, test commands, and maintenance instructions. Do not publish environment exports, API key prefixes, account identifiers, private hostnames, bucket names, balances, usage reports, chat text, file contents, database records, or signed URLs. Keep local evidence and recoverable backups in ignored, access-restricted storage. Inspect staged changes before every push.

The stable `v2.2.20` sync is the baseline for this ledger. Deployment and acceptance results belong to the applicable release evidence; this document must not imply that all optional integrations or upstream services have passed validation.
